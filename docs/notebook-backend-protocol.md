# Idea (deferred): NotebookBackend protocol

- **Status:** Proposed — **deferred, not implemented**
- **Created:** 2026-09-06 (during Phase 3 review of marimo version support)
- **Decision:** keep the current structure; introduce this seam when a marimo
  release actually shifts the private APIs.
- **Related:** [docs/marimo-version-support.md](marimo-version-support.md)
  (the version contract), `src/marimo_inspection/templates/`,
  `src/marimo_inspection/tools/lint.py`, `src/marimo_inspection/client.py`.

## The problem

The framework deliberately reaches into marimo's **private** APIs, which shift
between marimo releases without notice. Today that surface lives in two places:

1. **In-kernel (in every `templates/*.py`, ~800 lines)** — each file builds a
   *string* executed in the **live notebook kernel**:
   `import marimo._code_mode as cm`, `async with cm.get_context() as ctx:`,
   and (in `templates/lint.py`) `marimo._lint.diagnostic.Severity` /
   `RuleEngine`. Bound to the marimo version of the *running server*.
2. **In-process (`tools/lint.py`)** — imports
   `marimo._ast.parse.parse_notebook` and `marimo._lint.rule_engine.RuleEngine`
   and runs them in the MCP server process. Bound to the *installed* marimo.

`client.py` is pure HTTP against marimo's stable `/api/*` endpoints and
already needs no marimo imports — the future seam should keep it that way.

## The proposed seam

A single interface owning everything that varies with marimo's private APIs, so
the rest of the framework (server, tools, client) depends on the interface, not
on marimo:

```python
# backends/base.py
from typing import Protocol

class NotebookBackend(Protocol):
    name: str                                   # e.g. "0.24"

    # In-kernel: strings sent to the live kernel
    def cell_data_template(self, cell_ids: list[str]) -> str: ...
    def cell_map_template(self, ...) -> str: ...
    def cell_outputs_template(self, ...) -> str: ...
    def dependency_template(self, ...) -> str: ...
    def errors_template(self, ...) -> str: ...
    def variables_template(self, ...) -> str: ...
    def mutation_template(self, ...) -> str: ...
    def lint_template(self) -> str: ...

    # In-process: runs against the installed marimo
    async def lint_source(self, contents: str, filepath: str) -> dict: ...
```

Concrete implementations live beside it (e.g. `backends/v0_24.py` — the only
file allowed to import `marimo._code_mode` / `marimo._ast`; a
`backends/v0_25.py` added when a new version ships). A small factory picks the
backend from the installed `marimo.__version__` and raises a clear error for
unsupported versions. `tools/*` then call
`backend.cell_map_template(...)` / `await backend.lint_source(...)` instead
of importing template modules directly.

On a marimo bump you write/update one backend file and port the private-API
calls; the rest of the repo never changes.

## Why it was deferred

- Only one marimo version is ever installed *and* tested today (0.24.x), so the
  version-gated dispatch would have a single implementation — the abstraction
  would be speculative (YAGNI).
- It does **not** fully solve kernel/process drift: templates are generated by
  the *installed* marimo but executed by the *server's* marimo. The guarantee
  stays "tested combination only" (see marimo-version-support.md), protocol or
  not.
- Cost: mechanically reorganizing ~800 lines of templates + `tools/lint.py`
  behind the interface, for a seam nobody hits while marimo stays at 0.24.x.

## Trigger to revisit

- A new marimo minor/major ships and the private APIs shift (PyPI latest was
  still 0.24.0 when this was written), **or**
- The marimo-touching surface keeps growing and starts to be edited regularly
  across upgrades.

## How to validate when implementing

1. Port the current templates/lint into `backends/v0_24.py` unchanged; the
   existing unit suite must stay green (`uv run pytest -m "not live"`).
2. Add the factory + clear error for unsupported versions.
3. Re-run the live suite (`uv run pytest -m live`, boots its own headless
   server) — the in-kernel strings must behave identically.
4. Only then add a second backend for a newer marimo, and widen
   `marimo[recommended]>=0.24.0,<0.25` per marimo-version-support.md with the
   passing live suite as evidence.
