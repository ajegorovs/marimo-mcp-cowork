# marimo version support

The framework deliberately reaches into **private** marimo APIs. Private APIs
shift between marimo releases without notice, so the supported range is pinned
and validated — never assumed.

## Pinned range

`marimo[recommended]>=0.24.0,<0.25` (declared in `pyproject.toml`).

- `>=0.24.0` — the framework is built and tested against marimo **0.24.0**.
- `<0.25` — a hard upper bound. The *next* marimo release is treated as
  untested until the live suite runs green against it, at which point the bound
  is widened in the same commit that adds the evidence.

## Where the private APIs are touched

There are **two** marimo version contracts:

### 1. In-process (the MCP server process)

Runs on the **installed** `marimo` in the environment that launches
marimo-inspect. `client.py` itself is pure HTTP and imports **no** marimo
private APIs:

| Symbol | Location |
|---|---|
| `marimo._ast.parse.parse_notebook` | `src/marimo_inspection/tools/lint.py` |
| `marimo._lint.rule_engine.RuleEngine` | `src/marimo_inspection/tools/lint.py` |

### 2. In-kernel (scratchpad code)

Sent to the **live kernel** as generated strings; the kernel binds them to
whatever marimo version the running server has:

| Symbol | Generated by |
|---|---|
| `marimo._code_mode as cm` + `cm.get_context()` | every *live* template: `cell_map`, `cell_data`, `cell_outputs`, `dependency`, `errors`, `mutation`, `ui`, `variables` |
| `marimo._plugins.ui._core.ui_element.UIElement` (+ `element.value`) | `templates/ui.py` — the widget tool reads the element's declared input shape from the first parameter of its `UIElement[...]` generic base and reads its value back after the update |

> **`templates/lint.py` is dead code.** Lint runs **in-process** (see §1), not
> via a scratchpad template. `templates/lint.py` still imports
> `marimo._lint.diagnostic.Severity` and `RuleEngine`, but it is never imported
> by any tool — it is retained only for the template-shape unit tests
> (`test_templates.py`). It is **not** a live version contract and should not
> be counted as one.

The live test suite (`-m live`) couples both contracts to the *same* installed
marimo, because it boots the server with `python -m marimo edit` from that
environment. In production the two sides can in principle drift (a server built
on 0.25.x while marimo-inspect runs on 0.24.x); the in-kernel templates are
expected to keep working for 0.24.x-lineage kernels, but only the tested
combination is guaranteed.

### Cross-version evidence: a 3.14 kernel on marimo 0.24.x

What is pinned is the **marimo** version, not the kernel's Python minor. The one
piece of cross-Python evidence we have comes from the first consumer integration
(2026-09-07; the consumer's append-only log is
`udv-echo-process/docs/marimo-integration-log.md`, entries S11–S13 and O21):

| Side | marimo | Python |
| --- | --- | --- |
| Provider (`marimo-inspect`'s own venv) | 0.24.0 | 3.12 |
| Live kernel under test | 0.24.0 | **3.14.7** |

Against that kernel every live template ran clean — `cell_map`, `errors`,
`variables`, `cell_outputs`, and `edit_cell`'s `_code_mode.get_context()`
round-trip (O21: the full co-work loop ran green, `get_errors` reported 0
errors, `marimo check` exited 0) — **including error paths**: a hand-written
cross-cell redefinition was caught at runtime by `get_errors` as
`kind: "graph"` (S13). A provider-side probe the same day, recorded in
[agenda-remote-marimo-mcp.md](agenda-remote-marimo-mcp.md) §Evidence gathered,
observed the same combination independently.

Read it for exactly what it is, and no more:

- **Observed integration evidence, not a suite-enforced leg.** `-m live` boots
  its server from the dev environment (3.12), so the suite has no 3.14 leg and a
  regression that appears only on a 3.14 kernel would not be caught here.
  Adding that leg is open work, deliberately not claimed.
- It says nothing about a **0.25+ kernel** — the drift risk this document
  exists for — and nothing about marimo differing between the two sides.
- Same host, loopback; no network involved.

## Validating a marimo upgrade

Before widening `<0.25`:

1. Bump marimo in the dev environment (`uv add "marimo[recommended]>=<new>,<0.<new+1>"`).
2. Run the unit suite: `uv run pytest -m "not live"`.
3. Run the live suite: `uv run pytest -m live` (starts its own headless server).
4. Only if both pass, widen the upper bound and update this doc with the new
   tested version.

## Non-goal

We do **not** abstract the marimo internals behind a compatibility layer for
abstraction's sake — `tools/lint.py` (in-process) + the *live* templates
(`cell_map`, `cell_data`, `cell_outputs`, `dependency`, `errors`, `mutation`,
`ui`, `variables`) are deliberately the only files that change on a marimo bump
(`client.py` is pure HTTP). If that surface ever grows unwieldy, a thin
`NotebookBackend` protocol can isolate them further; that is a later,
optional step — see [notebook-backend-protocol.md](notebook-backend-protocol.md)
for the full deferred design (status, sketch, and the trigger to revisit).
